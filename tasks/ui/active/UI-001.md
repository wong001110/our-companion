# UI-001 — Align Friend Lookup Relationship States

## Status

Ready for review

## Objective

Correct the Social friend-code lookup UI so it matches the authoritative Network relationship contract and distinguishes no relationship, an existing friend, an incoming request, and an outgoing request without exposing blocking state.

## Base Commit

`5f58c9b3da0dc9549de6e482f1fe70ab82fcfba3`

## Branch

`main`

## Implementation Commit

## Problem Evidence

- The Network service returns `none`, `friend`, `incoming_request`, or `outgoing_request`.
- A blocked lookup returns the same `INVALID_FRIEND_CODE` not-found response as an invalid or unavailable code.
- The Client relationship message mapping expects `friends` and exposes `blocked`.
- The Client currently falls back unexpected relationship values to the no-relationship message.

## Scope

- Verify the authoritative Network lookup controller, service, and tests.
- Introduce a shared renderer-safe lookup relationship type.
- Align main-process, preload, shared, and renderer lookup types with the Network contract.
- Map each supported relationship to distinct English and Simplified Chinese copy.
- Show the send-request action only for `none`.
- Treat unexpected relationship values as a safe localized synchronization/unavailable state.
- Add focused automated coverage for all supported values and the fallback.
- Preserve the current Operational Paper layout and styling.

## Out of Scope

- Social page redesign or unrelated refactoring.
- Friend Code format or normalization changes.
- Friend-request backend behavior or Network code changes.
- Friends, request, presence, blocking, Visit, or Notifications behavior.
- New visual assets.
- Merge to `main`.

## Required Runtime States

1. Untouched lookup: no result or relationship announcement.
2. `none`: identity and no-relationship copy, with Send Friend Request available.
3. `friend`: distinct already-friends copy, without Send Friend Request.
4. `incoming_request`: distinct incoming-request copy, without Send Friend Request.
5. `outgoing_request`: distinct outgoing-request copy, without Send Friend Request.
6. Invalid/unavailable code: existing safe not-found behavior without blocking disclosure.
7. Unexpected relationship: safe localized synchronization/unavailable copy, no raw value or incorrect relationship claim.
8. Busy/failure: duplicate submission blocked, input remains usable, stale lookup is not presented as the failed query result.

## Acceptance Criteria

- Client types match the authoritative public Network contract.
- No production Client mapping expects `friends` or renderer-visible `blocked`.
- Only `none` renders Send Friend Request.
- All four supported values render distinct localized messages.
- Unexpected values fail safely and do not expose blocking state.
- English and Simplified Chinese remain in parity.
- No raw server message is primary UI copy.
- Lookup state is not communicated by color alone; keyboard and focus behavior remain functional.
- No raster asset or unrelated Social visual change is added.
- Focused tests cover all supported values and the unexpected-value fallback.
- Existing Social Electron coverage and the required project checks pass.
